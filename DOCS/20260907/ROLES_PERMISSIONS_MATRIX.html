Tier 1 · Executive

The security posture in one screen

There is no role hierarchy in this application. There is one binary — authenticated or not — plus a single email allow‑list guarding diagnostics in production.

Tokens in the browser Zero

The BFF invariant. The server holds the session; WASM receives a claims‑only principal. AddOidcAuthentication() is forbidden on the client.

Authorization default Fail-closed

A new endpoint is authenticated unless it explicitly calls .AllowAnonymous(). Forgetting to secure something is not a possible mistake here.

Named roles 0

No role claims are required anywhere in production code. X-Fake-Roles exists only for the Test environment's header‑driven handler.

Escape hatches 1

A middleware that stamps AllowAnonymous onto /_framework endpoints. Removing it produces a blank page — see Tier 2.

Fail-closed, stated precisely

AuthorizationOptions.FallbackPolicy = RequireAuthenticatedUser. Client‑side [Authorize] attributes are UI‑only and enforce nothing — they hide a nav link, they do not protect data. Every real guarantee in this table is server‑side.

Production without a client id throws by design rather than silently degrading to cookie‑only — a degraded auth mode that boots successfully is worse than a host that refuses to start.

Antiforgery is a filter, not the middleware

app.UseAntiforgery() alone does nothing for this API. It validates only what it recognises as a form post, so a JSON POST passes straight through regardless of IAntiforgeryMetadata. Real enforcement is AntiforgeryValidationFilter, applied at the group level.

  • ✓Apply .RequireAntiforgeryValidation() to the MapGroup, so a POST added to an existing group later is protected by default rather than by memory.
  • ✗Do not also set RequiresValidation = true. The middleware then marks the request unvalidated, the filter's own guard trips, and correct tokens are rejected.
  • ✓The client echoes the token in X-CSRF-TOKEN because it cannot read the HttpOnly cookie half.
  • ✓Tokens are identity‑bound. One issued while anonymous stops validating after sign‑in; AntiforgeryTokenHandler's single retry‑on‑400 exists for exactly that and is normal on a first authenticated write.
  • ✗The filter validates only POST, PUT, PATCH and DELETE. A GET inside a protected group is untouched.
The one escape hatch — do not remove it

The Blazor boot manifest under /_framework is runtime‑generated, not a static asset, so MapStaticAssets().AllowAnonymous() misses it. The fail‑closed fallback policy then 302s it to /login; the browser follows the redirect, receives login HTML where it expected a JS module, fails the subresource‑integrity check, and the app never boots — a blank page with no error. A middleware therefore stamps AllowAnonymous onto any /_framework endpoint lacking an explicit opt‑out. Every endpoint without that prefix stays fail‑closed.

Cookie hardening has an environment seam

The check gating cookie security is IsDevOrTest(), not IsDevelopment(). Integration and E2E run over plain HTTP, and CookieSecurePolicy.Always would make the browser silently discard the auth cookie: /dev-login still answers 302 with a Set-Cookie, the log looks clean, and every subsequent request is anonymous.

Worth knowing about the anonymous AI endpoints

Five AI endpoints are deliberately anonymous so an unauthenticated visitor can try the app. They are the ones that spend money, so the rate limiter is their only cost control: with no NameIdentifier claim it partitions by remote IP, then by the literal string "anonymous" if even that is unavailable. /api/bulk-generate/batch reaches this path while fanning out up to four concurrent image generations per call.

Policy definitions

// Features/Shared/AuthorizationPolicies.cs — the name lives here so neither slice
// depends on the other. The behaviour lives in AuthServiceExtensions.
public const string Diagnostics = "DiagnosticsAccess";

// AuthServiceExtensions.cs
options.FallbackPolicy = new AuthorizationPolicyBuilder()
    .RequireAuthenticatedUser()
    .Build();                                  // ← the fail-closed default

options.AddPolicy(DiagnosticsPolicy, policy => policy.RequireAssertion(ctx =>
{
    // Non-Production: any authenticated user may read diagnostics.
    // Production: the identity's email must be on the allow-list.
    // An EMPTY list denies everyone — fail-closed, not fail-open.
    var admins = (configuration[ConfigKeys.DiagnosticsAdminEmails] ?? string.Empty)
        .Split(',', StringSplitOptions.RemoveEmptyEntries | TrimEntries);

    return ctx.User.Claims.Any(c =>
        (c.Type is ClaimTypes.Email or ClaimTypes.Name or "email" or "preferred_username")
        && admins.Contains(c.Value, StringComparer.OrdinalIgnoreCase));
}));

Cookie hardening

// §4.2 BFF cookie hardening — HardenCookie(options, environment)
options.Cookie.HttpOnly     = true;                 // never readable by WASM or JS
options.Cookie.SameSite     = SameSiteMode.Strict;  // not sent on cross-site navigations
options.Cookie.SecurePolicy = environment.IsDevOrTest()
    ? CookieSecurePolicy.SameAsRequest                // HTTP test tiers
    : CookieSecurePolicy.Always;

// The OIDC nonce and correlation cookies keep their own SameSite=None; Secure
// defaults, so the handshake still completes under a Strict session cookie.

Refusal payloads

Both refusals come from the framework's problem‑details writer. The distinction matters for the client: 401 means "sign in and retry", 403 means "signing in again will not help".
