Tier 1 · Executive

Topology and the rules that hold it together

The architecture is deliberately hybrid, and knowing which half you are in decides how you add a feature.

Server style Vertical slice

A new feature is a new folder under Features/ with its endpoint, DTO and validator together. VSA beats Onion when both would apply.

Cross-slice primitives 3 layers

Domain, Application, Infrastructure exist only to supply what more than one slice needs. Adding a layer for one feature will fail review.

Browser assemblies 2

Only .Client and .Shared ship to the browser. Three rules assert that server code and the Azure SDKs never follow them there.

Render mode WASM, no prerender

The WASM client owns the only DI container, so a server prerender pass could not resolve its services. Not a performance choice.

Boundary rules, as enforced

PoRedoImage.Tests.Architecture holds a rule registry rather than one test method per rule, so 26 rules cost two methods against the tier's ceiling. They run in CI on every push.

CategoryRulesAsserts
Core isolation5Domain depends on nothing — not Application, not Infrastructure, not the host, not ASP.NET Core.
Persistence isolation1Domain holds no Azure.Data.Tables or Azure.Storage types.
Layer boundaries5Application reaches Domain abstractions only; Infrastructure never reaches the host or the client.
Contract isolation3Shared touches no server layer, no client, and no Azure SDK — it must stay trim‑safe.
Browser boundary3Client never references Infrastructure, the host assembly, or Azure.Identity.
Vertical slice encapsulation9Each named slice must not depend on a sibling slice.
Gap worth knowing about

The slice‑isolation list names nine slices: Auth, BulkGenerate, Diagnostics, Idempotency, ImageAnalysis, MemeTemplates, Pricing, RapRoast, UserImages. VideoGenerate is not among them — it is the newest slice and was not added to the registry, so nothing currently asserts that it stays free of its siblings. Adding the string to Slices costs no additional test methods.

Test tiers and their headroom

Each tier enforces its own method ceiling, and exceeding one breaks the build rather than warning. A [Theory] counts once regardless of how many InlineData rows it carries, which is the lever to reach for before raising a ceiling.

Two things this ERD is telling you

1. There is no foreign key from blob to table row — the relationship is the blob name convention {userId}/{imageId}. Delete has to remove both, and they can drift.

2. BulkPrompt.PartitionKey is the constant literal "prompts", not a user id. The prompt board is therefore global, not per‑user: every authenticated caller reads and writes the same partition. The endpoints require authentication, but they do not scope by identity the way /api/user-images does.

The Bicep template references the App Service plan and never creates, updates or deletes it: the plan's home stamp is fixed by Azure at creation time, so the live instance cannot be migrated without a clone (new hostname) or a destroy‑and‑recreate. A blob lifecycle policy tiers to cool at 7 days and deletes at 30 — generated images are not archival.

Routing, registration and schema

Root routing architecture

Route precedence does real work here. A literal first segment outranks a catch‑all, which is what keeps a mistyped API path returning JSON instead of an HTML document.

Order bug this codebase already paid for

The mock decision is resolved in exactly one place. MockAiGate.IsEnabled runs in the host and its result is passed into Infrastructure, because that assembly deliberately has no ASP.NET types in scope. In mock mode each concrete mock is registered once and surfaced under both its service interface and IMockable, so the "USING MOCK DATA" banner can enumerate reasons without constructing the service twice.

// UserImageId — a value type whose only job is to be safe as a key.
// Guid.TryParseExact with "N" rejects braces, hyphens and any non-hex character:
// precisely the set that would break a blob name or a Table Storage RowKey.
public readonly record struct UserImageId
{
    public static UserImageId New()   => new(Guid.NewGuid().ToString("N"));
    public static UserImageId Parse(string v);          // throws with the value in the message
    public static bool TryParse(string? v, out UserImageId id);
}

Build gates

Directory.Build.props applies to every project: net10.0, Nullable, TreatWarningsAsErrors, EnableTrimAnalyzer (diagnostics only — IsTrimmable stays off), and NuGet audit at low, so a vulnerable package breaks the build. Packages are centrally managed; a PackageReference with an inline version will not build. Versioning is MinVer from git tags. 

// Because warnings are errors, IL2026 from the trim analyzer breaks the build.
// Three deliberate suppressions exist in Program.cs, each with its reason:
#pragma warning disable IL2026
  1. Razor component registration   — reflective by nature
  2. Options binding                — the option types use init-only properties, which the
                                    configuration binding source generator cannot assign.
                                    Enabling it silently binds every value to empty and the
                                    host fail-fasts at startup.
  3. The anonymous health payload   — the deploy smoke test greps that exact shape
#pragma warning restore IL2026

// Everywhere else: use ConfigValue.Bool / Float / Double, never ConfigurationBinder.GetValue<T>.
Why the Android head lives in its own solution

PoRedoImage.Mobile is the only project using TargetFrameworks (plural), and Directory.Build.props is imported before the project body, so its "no TFM set yet" guard stamps on TargetFramework=net10.0. Left in place that beats TargetFrameworks and the solution build tries to build the MAUI head as plain net10.0 (NETSDK1005). The csproj clears it with an empty <TargetFramework></TargetFramework>. The head moved to PoRedoImage.Mobile.slnx so the main solution stays pure net10.0 and ubuntu-latest restore no longer dies on the missing maui-android workload.
