04

Layer leaks

where the onion is pierced, and whether it matters

Application → Shared

Deliberate

In a strict onion, the Application layer would define its own result types and the Web layer would map them to transport DTOs. Here ImageAnalysisOrchestrator returns ImageAnalysisResponse — a Shared DTO — straight to the endpoint.

Cost: a change to the wire contract reaches into the Application layer. Benefit: one type instead of two plus a mapper, on a contract with a single consumer.

Assessment: proportionate for a solution this size. It would become a real cost the moment a second transport (gRPC, a queue consumer) needed a different shape.

Client → Domain

Narrow

The WASM client references Domain for two things only: the IMockable interface — so RemoteMockFlag can register server-reported mock reasons into client DI and drive the banner — and the UserImageKind enum.

Cost: the whole Domain assembly ships to the browser for two types. It is small and has no dependencies, so the download cost is marginal, but the conceptual coupling is real: a domain refactor can now break the client build.

Assessment: the cheapest fix is to move both types to Shared, which the client already references. That would delete an edge outright.

What is not leaking Infrastructure is invisible to Web's feature code. The host references the assembly only to call AddPoRedoImageInfrastructure(configuration); every endpoint binds to a Domain port. Swapping Gemini for another provider touches one DI file. The mock ladder is proof the seam works: Mocks:UseMockAi=true substitutes six services without an endpoint knowing.

Shared contract surface

everything both runtimes can see

PoRedoImage.Shared is the only assembly compiled into both the browser and the server. Anything added here is, by construction, part of the public client/server contract — so its contents are the honest measure of coupling between the two runtimes.

Non-DTO shared surface

Shared/Configuration · Imaging · Json · Validation
ConfigKeys
The full configuration-key vocabulary as constants, so no slice types a key as a magic string.
AiProviderIds
Provider ids namespaced by execution location — remote:, ollama:, browser:. The previous scheme matched bare model-name prefixes and could not tell a browser model from an Ollama one; VisionServiceRouter now does an explicit namespace check.
ImageBytes
Shared image-payload handling, used on both sides of the wire.
SharedJsonContext
Source-generated serialization metadata — the reason the DTO path is reflection-free and trim-safe.
MaxCountAttribute
MaxItemLengthAttribute
Validation attributes applied to request DTOs, so the same rule runs client-side and in the server's ValidationFilter.
One consequence worth flagging Because validation attributes live in Shared, the client and server enforce literally the same rule object — there is no second copy to drift. That is the strongest isolation property in this codebase, and it comes free from putting the attribute in the shared assembly rather than duplicating the constraint.

Slice autonomy

do slices reference each other?

Cross-slice references inside Web/Features

1 shared vocabulary, 0 direct references
Direct slice→slice
None. No Features/X type names a Features/Y type.
Shared filters
ValidationFilter<T> and IdempotencyKeyFilter live in their own folders (Features/Shared, Features/Idempotency) and are applied by the consuming slice — a dependency on infrastructure, not on a peer.
Policy names
The one genuinely cross-slice concept: Auth defines the DiagnosticsAccess policy, Diagnostics requires it. Resolved by putting the constant in Features/Shared/AuthorizationPolicies.cs — both depend on the vocabulary, neither on the other.
Pricing → ImageGen
PricingEndpoints reads the ImageGen:Provider config key to pick which price block to return. Coupled through configuration, not code.
