The auth engine switch

evaluated once, in AddPoRedoImageAuth

Three mutually exclusive branches. The order matters: the fake-auth bypass is checked first and returns early, so when it is active no cookie or OIDC handler is ever registered.

Branch 3 was previously gated on IsDevelopment() alone. That let the Test environment fall through to the OIDC branch and construct the handler with an empty ClientId, which threw and took down the entire integration suite — the reason the condition is now not Production rather than is Development.

FakeAuth — how it is fenced off

Header-driven identity

A request authenticates itself by sending X-Fake-User. Any caller can therefore assume any identity and any role set — which is exactly what makes it useful for tests and catastrophic in production.

Fence 1
Registration is guarded by !environment.IsProduction().
Fence 2
The handler's constructor throws in Production — defence in depth, so even a misconfigured registration cannot start the app.
Graceful absence
No X-Fake-User header returns NoResult, so anonymous endpoints still serve and protected ones return 401 — identical to the real pipeline.

Cookie hardening

HardenCookie()
HttpOnly
true — never readable by WASM or JavaScript. This is the property the whole BFF model rests on.
SameSite
Strict — not sent on cross-site navigations. The OIDC nonce and correlation cookies keep their own SameSite=None; Secure defaults so the handshake still completes.
Secure
Always outside Development; SameAsRequest locally so the http://localhost:4000 F5 loop works.
Login path
/login. Access-denied goes to /access-denied under OIDC and to /login under cookie-only.

Correlation chain

browser → BFF → provider
Client stamps
X-Session-ID — stable per browser tab. X-Correlation-ID — fresh per request. Existing headers are never overwritten, so a caller correlating its own retry keeps its id.
Server reads
RequestContextMiddleware takes both, generates fallbacks (a GUID; TraceIdentifier for session), echoes them in the response, and stores them in HttpContext.Items.
Logging
CorrelationId, UserId and SessionId are pushed into the Serilog LogContext for the whole request scope.
Outbound leg
OutboundCorrelationHandler re-stamps both headers on the Ollama, GeminiApi and HuggingFaceApi named clients — re-opened by name in Program.cs because Infrastructure is a plain project and cannot see IHttpContextAccessor.
05

Two rules that keep the SPA working

both are load-bearing

API callers get 401, never 302

enforced in two places

A WASM fetch follows redirects transparently. Without this rule a call to a protected route would silently receive login HTML with status 200 and fail in a way that is very hard to diagnose.

Cookie handler
OnRedirectToLogin → sets 401 when the path starts /api, otherwise redirects normally.
OIDC handler
OnRedirectToIdentityProvider → sets 401 and calls HandleResponse() for /api paths, suppressing the jump to Microsoft.
Status-code pages
UseStatusCodePagesWithReExecute is wrapped in UseWhen(!path.StartsWith("/api")), so an API 404 stays a 404.

The /_framework opt-out

without it: blank page

The whole UI — including /login — is Interactive WebAssembly and cannot boot without its runtime assets. Most are static files covered by MapStaticAssets().AllowAnonymous().

The runtime-generated boot manifest resource-collection.js is not a static asset, so the fail-closed fallback policy 302s it to /login. The browser follows, gets HTML instead of a JS module, fails the subresource-integrity check, and renders nothing.

The mitigation re-tags any /_framework endpoint lacking an explicit IAllowAnonymous — after routing has matched, before authorization evaluates. Everything without that prefix stays fail-closed.
