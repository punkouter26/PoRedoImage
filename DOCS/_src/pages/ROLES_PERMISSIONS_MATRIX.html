Beyond the binary

controls that are not authorization but act like it

Ownership — the real access control

enforced server-side

The gallery is the one place a user's data is separated from another's, and it does not use a role. Every /api/user-images handler reads ClaimTypes.NameIdentifier from the caller and returns Unauthorized if it is absent.

Blob layout
user-images/{userId}/{imageId}
Table layout
PartitionKey = userId, RowKey = imageId
Container access
PublicAccessType.None — bytes are proxied through the API, never served directly from storage
Effect
Ownership is structural: another user's id produces a different partition, so a cross-user read is not merely denied, it addresses nothing.

The diagnostics allow-list

the only privilege tier

In Production, DiagnosticsAccess requires a claim matching Diagnostics:AdminEmails. Outside Production, any authenticated user passes.

Claim types checked
Email, Name, email, preferred_username — four, because different issuers populate different ones
Comparison
Case-insensitive membership in the configured list
Empty list
Denies everyone. The assertion requires admins.Length > 0 before any claim is examined — fail-closed by construction, not by configuration discipline.
Why it matters
The endpoint exposes masked infrastructure topology. Masked is not secret-free: knowing which Key Vault and tenant are in play is useful to an attacker.
If roles were introduced The wiring already exists. FakeAuthHandler emits ClaimTypes.Role from X-Fake-Roles, so the E2E suite could drive role scenarios today. Entra ID app roles would arrive in the same claim type through OIDC. The change is narrow: add policies beside DiagnosticsAccess in AddPoRedoImageAuthorization, name them in Features/Shared/AuthorizationPolicies.cs, and attach them per group — the pattern /api/diag already demonstrates end to end.
