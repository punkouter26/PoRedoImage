Why "time to interactive", not "page load" The document's load event fires in roughly 30 ms on this app — and means almost nothing, because blazor.web.js fetches and starts the .NET runtime asynchronously after it. Charting loadEventEnd would show a flat, flattering line while the user still stared at a loading spinner. The blue series is instead measured from inside the running app, at the moment the first component renders: navigation start → actually usable. The orange series is kept alongside it purely to show how large the gap is.
Why CLS and memory are two charts, not one CLS is a unitless score around 0.05; the heap is tens of megabytes. Plotting them together would need two y-axes on one frame — which makes the crossings and relative slopes an artefact of where each axis was zeroed, not a fact about the data. Small multiples say the same thing without the distortion. The x-axis is shared, so they still read as one window.

Sampling policy

ErrorPreservingSampler.cs
Routine spans
Sampled at a configured ratio — 10% in Production.
Error-bearing spans
Always kept when the error is known at span start: an error=true tag or an HTTP status ≥ 500.
Trace integrity
Wraps ParentBasedSampler, so a sampled-in trace keeps all of its children rather than fragmenting one operation across the sampling boundary.
The head-sampling gap
A request that throws later cannot be rescued by a head sampler. That case is covered separately: the Serilog → Application Insights sink exports every logged exception at 100%, unsampled.

Secret masking on /api/diag

DiagnosticsEndpoints.MaskValue

Twelve configuration values are exposed for diagnosis. Nine are masked; three (MinTagConfidence, the chat deployment name, and the environment) are returned in full because they are not secrets.

04

How the data gets here

collector to chart, in order

1 · Collect
Client/wwwroot/js/vitals.js reads PerformanceNavigationTiming for load and DOMContentLoaded, accumulates layout-shift entries via PerformanceObserver, and reads both the JS heap and the WebAssembly linear memory. It is loaded before the Blazor script tag on purpose — install the observer later and the boot's own layout shift goes unmeasured, which is the shift a WASM app most needs to see.
2 · Report
ClientVitalsReporter waits for load plus a 2.5 s settle window, then POSTs once per app load. ClientVitalsProbe in the layout starts it; the call is fire-and-forget and swallows every failure, because telemetry must never degrade the experience it measures.
3 · Store
AzureTableClientVitalsRepository writes to the ClientVitals table, PartitionKey = UTC day, RowKey = inverted tick count. The inversion is what makes "most recent N" a Take(n) instead of a full scan — Table Storage cannot reverse a query's order.
4 · Serve
GET /api/diag/vitals returns the history behind the same DiagnosticsAccess policy that guards /api/diag. The write path needs only an authenticated user, since every signed-in browser produces samples.
5 · Export
node DOCS/export-vitals.mjs pulls the history into DOCS/diagnostic_history.json; node DOCS/build.mjs --no-mmd inlines it here. Inlined rather than fetched because this page is opened over file://, where fetching a sibling JSON is blocked.
Known limits of the collector One sample per app load, not per navigation — PerformanceNavigationTiming describes the document, and a client-side route change does not produce a new one. The heap figure is engine-dependent: performance.memory is Chromium-only and the WASM linear memory is read through the .NET runtime handle, so both are null on engines that do not expose them; the chart falls back to whichever is available. Retention is manual — Table Storage has no TTL, and nothing purges old partitions yet.
