PoRedoImage System Portal

A Blazor WebAssembly photo studio on an ASP.NET Core backend-for-frontend, and the five reports that describe how it routes, guards, bills and degrades.

What this system is

TIER 1

A photo goes in; something else comes out — a repainted version of it, a captioned meme, a roast verse performed over a beat, an eight-second clip. The browser does all of the rendering: PoRedoImage.Client is a Blazor WebAssembly SPA that owns every interactive page and the only wwwroot in the solution. PoRedoImage.Web hosts it as a backend-for-frontend: it holds every provider key, and no token ever reaches the browser. The server authenticates with an HttpOnly, SameSite=Strict cookie and serialises a claims-only principal across the WASM boundary, so the client can render <AuthorizeView> without ever holding a credential.

Behind the BFF sits a small fleet of AI backends, chosen per capability rather than once globally: Azure Computer Vision and Azure OpenAI for reading images, Google Gemini for painting them, Google Lyria for performing lyrics, Google Veo for animating a still — plus two execution locations that are not servers at all, a WebGPU runtime in the browser and ONNX Runtime GenAI on an Android phone. Every provider id is namespaced by where it runs (remote:, ollama:, browser:, device:) because an earlier scheme matched bare model-name prefixes and could not tell a browser model from an Ollama one.

Every one of those calls can fail, and the shape of this codebase is set by what happens when they do. Callers of the chat, vision and image services catch failures and substitute canned output, so a broken provider degrades several features at once while /health still reports green. That is not hypothetical: a HuggingFace image provider returned HTTP 400 for every configured model and then ran out of credits, and nothing surfaced — it was removed in August 2026 and must not return without an explicit decision. The rule the incident produced runs through every report here.

The invariant

Any new fallback path must set a user-facing reason. DescriptionFallbackReason, RefusalReason, FallbackReason exist because silent degradation reads to the user as “the AI ignored my photo”. A degraded answer with no explanation is treated as a defect, not a graceful recovery.

Four things to know first

TIER 1
System architecture

Two web projects, one of which ships

Only .Client reaches the browser. .Web is a host document plus an API; a new interactive page there would never render. Server code is vertical-slice under Features/ — a new feature is a new slice, never a new layer.

External integrations

Per-capability routing, one provider deep

IVisionServiceRouter resolves per request on the id namespace; IChatCompletionService resolves once at startup. Image generation has a single real implementation — the router survives as the slot where a second provider returns.

Auth strategy

The browser never holds a token

Three modes resolved at startup: header-driven fake auth (test/dev), cookie-only when no AzureAd:ClientId is set, and Entra OIDC + cookie otherwise. Production without a ClientId throws by design rather than degrading silently.

Target SLAs

Budgets, not promises

The repository fixes timeout ceilings rather than published SLOs. The one stated target is the bulk board's 45 s p95 — the reason ten sequential uploads became one streamed NDJSON batch.

Standard payload envelopes

TIER 3

Three shapes cover every response. Serialization runs through SharedJsonOptions.CreateResolver() on both sides of the WASM boundary, with DefaultIgnoreCondition = WhenWritingNull, so an omitted optional field means “not set” rather than null on the wire.

Error — RFC 7807 / 9457

// every Results.Problem(...) call site
Content-Type: application/problem+json
{
  "type":   "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title":  "Validation Error",
  "status": 400,
  "detail": "DescriptionLength must be between 200 and 500. Provided: 900"
}
Client deserialises into ProblemDetailsDto — WASM cannot reference the server-only ProblemDetails.

Health — anonymous projection

GET /health → application/json
{
  "Status": "Healthy",
  "Duration": 412.7,
  "Entries": [
    { "Key": "key-vault",       "Status": "Healthy",  ... },
    { "Key": "computer-vision", "Status": "Healthy",  ... },
    { "Key": "openai",          "Status": "Healthy",  ... },
    { "Key": "table-storage",   "Status": "Healthy",  ... },
    { "Key": "imagen3",         "Status": "Degraded", ... }

Enum written as a string so the post-deploy smoke test can grep the failing check name. /alive runs no checks at all.

Streamed batch — NDJSON

POST /api/bulk-generate/batch
Content-Type: application/x-ndjson
Cache-Control: no-cache, no-store
X-Accel-Buffering: no

{"index":3,"imageData":"iVBORw0…","contentType":"image/png"}
{"index":0,"imageData":"iVBORw0…","contentType":"image/png"}
{"index":7,"error":"Gemini declined this prompt."}
One JSON object per line, flushed the moment a slot lands. Slots complete out of order under a concurrency cap of 4; one failure never fails the batch.
Why not SSE

The payloads are base64 images measured in hundreds of kilobytes, and SSE's data: line framing would have to re-chunk every one. NDJSON also degrades honestly: a client that does not stream still receives a parseable body, just all at once.

Distributed tracing conventions

TIER 3

Two headers travel the whole path, including the outbound leg to Ollama and the Gemini estate. Three properties are pushed into every log line — but not at the same hop, and the ordering is load-bearing.

KeyKindSet byBehaviour
X-Correlation-IDHeader, in + out RequestContextMiddleware Read from the request, else a fresh GUID. Echoed on the response and re-stamped on downstream calls by OutboundCorrelationHandler.
X-Session-IDHeader, in + out ClientRequestContext (browser) Stable per browser tab. Falls back to HttpContext.TraceIdentifier when the caller is not the WASM client.
CorrelationId, SessionIdSerilog property Pre-authentication Pushed before UseAuthentication(), because response headers must be set before anything writes a body and a rate-limited request still needs an id.
UserIdSerilog property UserContextMiddleware, post-auth Resolves NameIdentifier → Identity.Name → anonymous. It sits here and not with the other two for a measured reason — see below.
Application, Environment, MachineName Serilog enricherStartup Constant per process. Application is always PoRedoImage.
cloud_RoleNameOpenTelemetry resourceStartup Resolved from the entry assembly name so App Insights never shows unknown_service:dotnet.
ApplicationInsights:SamplingRatioTrace samplingConfig 1.0 in Development, 0.1 in Production — set explicitly in infra/main.bicep so the budget is auditable in the portal rather than an invisible code default.
Why UserId is pushed late

It used to be read alongside the correlation id, at a point in the pipeline where the cookie has not been decoded. The property was therefore the literal string anonymous on every log line ever written — 26,247 of 26,247 entries on a day with 53 successful logins. Per-user tracing was impossible until the push moved after UseAuthentication().

Why static assets log at Verbose

Every WASM boot wrote roughly 200 Information lines, one per /_framework/*.wasm fetch — 26,267 entries and 12.5 MB of log file in a single day of local use, and the identical volume billed as Application Insights ingestion in production. A failed or slow asset fetch still logs; the level only drops for the successful, fast, uninteresting ones.
