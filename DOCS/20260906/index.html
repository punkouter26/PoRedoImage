How the app actually works

A person lands on the Studio board at / and drops a photo into the intake bay. Nothing has been sent anywhere yet — the board simply flips each service row from awaiting photo to ready, and the five services (Regeneration, Meme, Bulk Generate, Rap Roast, Video) become one click away. That whole UI is WebAssembly: the .Client assembly owns Routes.razor, every interactive page, and the only wwwroot in the solution. The .Web project renders nothing but a host document, and prerendering is off deliberately — the WASM client owns the only DI container, so a server prerender pass could not resolve ImageSessionService or the deserialized auth state.

Four of the five services are request/response: the browser POSTs base64 image bytes to a minimal API and an Application-layer orchestrator takes over. Video is the exception — a Veo render takes minutes, so POST /api/video/generate hands back the provider's operation handle and the page polls GET /api/video/status every six seconds against an eight-minute budget. The orchestrator's shape is the same everywhere: look at the photo, reason about what it saw, then produce something. What varies is which calls get skipped. If the client already ran a browser-local vision model, it ships the result as PrecomputedDescription and the server skips its own vision call entirely — re-running it would bill a metered API for work already done for free. The same holds for PrecomputedEnhancedPrompt. Rap Roast goes further and folds two Azure Computer Vision calls into one, because Azure takes OCR, dense captions, objects and people in a single request; when the backend cannot combine them, the two calls still happen but concurrently, since neither depends on the other.

The part worth internalising is how this system fails. Almost every caller of a chat, vision or image service catches the failure and substitutes canned output. That is why a HuggingFace outage went unnoticed until its credits ran dry, and why the codebase now carries a standing rule: any new fallback path must set a user-facing reason. RapRoastResponse.DescriptionFallbackReason and ImageAnalysisResponse.DescriptionFallbackReason exist precisely so silent degradation stops reading to the user as “the AI ignored my photo”. The one place fallback is forbidden is local inference: a LocalInferenceException from a browser model surfaces verbatim rather than quietly re-routing to a metered provider, because silently billing someone who chose a free on-device model is a surprise charge.

Two rows that surprise people

/api/pricing never calls .AllowAnonymous(), so the fail-closed FallbackPolicy makes it authenticated. That is the correct default, but it is implicit — the client's session cost meter only loads once someone is signed in.

/api/video is the only AI slice with no rate limit, and it is also the most expensive action in the app at $0.40 per clip — ten image generations. Authentication and CSRF do bound it to signed-in callers, which the anonymous AI endpoints are not, but there is no per-user throughput cap.

/_framework/* is opened by a hand-written middleware, not by MapStaticAssets().AllowAnonymous(): the runtime-generated boot manifest is not a static asset, so the fallback policy 302s it to /login, the browser's subresource-integrity check then fails, and the app never boots. Removing that middleware produces a blank page.

Response envelope schemas

There is no wrapper envelope. A success is the bare DTO; a failure is RFC 9457 application/problem+json produced by Results.Problem(...). One endpoint streams instead.

// Success — the DTO itself, no wrapper
{ "description": "...", "tags": ["..."], "confidenceScore": 0.87,
  "regeneratedImageData": "<base64>", "regeneratedImageContentType": "image/png",
  "descriptionFallbackReason": null,
  "metrics": { "imageAnalysisTimeMs": 412, "descriptionGenerationTimeMs": 900,
               "imageRegenerationTimeMs": 6180, "descriptionTokensUsed": 214,
               "totalProcessingTimeMs": 7492, "errorInfo": null } }

// Failure — RFC 9457 problem+json
{ "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "Invalid Image", "status": 400,
  "detail": "Unsupported image format." }

// POST /api/bulk-generate/batch — NDJSON, one BulkBatchItem per line
{"index":0,"imageData":"<base64>","contentType":"image/png","error":null}
{"index":1,"imageData":null,"contentType":null,"error":"Gemini declined this prompt."}

Serialization runs through SharedJsonOptions.CreateResolver() on both sides of the WASM boundary, with DefaultIgnoreCondition = WhenWritingNull. The NDJSON writer uses the source-generated SharedJsonContext.Default.BulkBatchItem rather than the reflective overload, because the solution-wide trim analyzer rejects the latter (IL2026).

Why static assets log at Verbose

Serilog's GetLevel callback drops successful static-asset requests to Verbose, below the configured minimum. Without it, every WASM boot wrote roughly 200 Information lines — 26,267 entries and 12.5 MB of log file in a single day of local use, and the identical volume billed as Application Insights ingestion in production. A slow or failing asset fetch still logs; only the boring ones drop.
