Report 03 · What the user does and what the system does back

User Workflows

Six transformations, three response shapes — a plain JSON round trip, a streamed NDJSON batch, and a start-then-poll job — traced from the upload control to the blob.

Everything starts with one photo

TIER 1

A single image is picked once and held in ImageSessionService for the browser session, so moving between features does not mean re-uploading. Every feature page inherits the same intake rules from FeaturePageBase.

Accepted

JPG, PNG, WebP

Checked twice: by extension in the browser, and again on the server by magic bytes, which additionally recognise GIF and BMP and return a specific hint for HEIC. The declared content type is a hint, never the decision.

Bounded

20 MB, 1568 px

The same 20 MB ceiling on both sides, with the Kestrel request body capped at 25 MB to leave room for the JSON envelope. Images are downscaled to a 1568 px longest edge before upload — past that point nothing downstream resolves more detail.

Reused

Result chaining

Each results panel offers a “send result to…” row built from the same feature catalogue the Studio renders. The output of one feature becomes the active image of the next, and the vision cache means re-reading it costs nothing.

Three response shapes

TIER 1

Which one a feature uses is decided by how long the work takes and whether partial results are useful before the whole is done.

Shape 1 — request / response

One POST, one JSON body

Regeneration, Meme, Rap Roast, Style Director, template render. The client shows a staged progress message and reads the body as a string first, because a multi-megabyte payload takes a noticeable moment to deserialise on the WASM side.

Shape 2 — streamed

NDJSON, a line per slot

The bulk board. The image travels once, the server fans out under a concurrency cap, and each slot is flushed the instant it lands. Slots complete out of order; a failed slot carries an error and never fails the batch.

Shape 3 — start and poll

Operation handle

Video. POST /generate returns the provider's job handle immediately; the client passes it back to GET /status until done. A render outlives any reasonable HTTP response.

Why the two skips exist

A user who selected an on-device model has already said they want that trade. Re-running vision or the prompt rewrite server-side would bill a metered API for work already done for free — and if the local run fails, nothing falls back to a paid provider, because silently billing someone who chose a free model is a surprise charge.

Shape 2 — the bulk board

TIER 2

This replaced ten sequential POSTs driven by a for loop in the browser. That shape re-uploaded the source image with every request, turning a 4 MB photo into roughly 53 MB of base64 upload for one batch, and took about 40 s of wall clock against a 45 s p95 target it was only just meeting.

The operation handle is untrusted input

It comes from the client and reaches the provider URL as a path segment, so GET /api/video/status requires it to contain operations/ and rejects .. or a leading slash — a crafted value must not be able to walk the path onto a different endpoint.

Request contracts

TIER 3

All shared DTOs live in PoRedoImage.Shared, which must stay trim-safe: both the WASM client's call sites and the minimal APIs serialise through one resolver chain built by SharedJsonOptions.CreateResolver().

POST /api/images/analyze

class ImageAnalysisRequest
{
  [Required]              string  ImageData;
  [Required]              string  ContentType;
                          string  FileName;
  [Range(200, 500)]       int     DescriptionLength = 200;
                          ProcessingMode Mode;   // Regeneration | Meme
                          string? ModelId;            // vision provider id
                          string? ImageGenModelId;

  // on-device shortcuts — each removes a metered call
  [StringLength(4000)]    string? PrecomputedDescription;
  [MaxCount(20)]
  [MaxItemLength(100)]    IReadOnlyList<string>? PrecomputedTags;
                          string? PrecomputedEnhancedPrompt;
}
The caps on the precomputed fields are not arbitrary: this is client-supplied free text that flows verbatim into a metered model as prompt tokens. The endpoint is rate-limited, but a field that becomes billable tokens still carries a bound.

POST /api/rap-roast

class RapRoastRequest
{
  [Required] string  ImageData;
  [Required] string  ContentType;
             string? ModelId;
             RapStyle        Style     = BoomBap;  // | Trap | OldSchool
             RoastIntensity  Intensity = Roast;    // Gentle | Roast | Scorched
}
Both enums keep their initialiser when the JSON omits them, so a client that predates Intensity behaves exactly as it always did. Every level sits inside the same content guardrail — the dial changes how hard a jab lands, never what it may land on.

Validation, in the order it runs

TIER 3
StageWhereRejects withDetail
1 — file pickerImageLoadHelper.LoadAsync (browser)Inline messageExtension must be .jpg/.jpeg/.png/.webp; size ≤ 20 MB; then downscale to a 1568 px longest edge when a JS runtime is available.
2 — request bodyKestrel + FormOptions41325 MB ceiling — the 20 MB image cap plus JSON envelope overhead. Prevents a 50 MB base64 payload from exhausting the worker.
3 — DataAnnotationsValidationFilter<T>400 problem+jsonMinimal APIs do not run [Required]/[Range] automatically; this filter bridges that. All failing messages are joined into one detail.
4 — handler guardsEach slice endpoint400Deliberately redundant with stage 3 on the analyze path — the range check is repeated in the handler so the contract holds even if the filter is ever detached.
5 — image identityImageBytes.FromBase64400 “Invalid Image”Strips an optional data-URI prefix, decodes into an exact-size buffer, then resolves the real type from magic bytes. Replaced seven copies of the same try/Convert.FromBase64String pair.
6 — provider readinessIsConfigured503Checked before any work begins, so an unconfigured key is a clear 503 rather than a 500 from deep inside a client.
7 — upstream refusalEndpoint catch clauses422Content-filter refusals are matched on message text under both vendor spellings — Azure's content_filter and OpenAI.com's content_policy_violation. Matching only the latter left every Azure refusal falling through to an opaque 500.

The client's handler chain

TIER 3

Order matters: a replayed request must keep its correlation headers and pick up a fresh CSRF token, so the antiforgery handler sits inside the correlation handler.

new HttpClient(
  new CorrelationHeaderHandler(clientRequestContext)   // X-Correlation-ID, X-Session-ID
  {
    InnerHandler = new AntiforgeryTokenHandler(          // X-CSRF-TOKEN, one retry on 400
      () => new HttpClient { BaseAddress = base, Timeout = 30 s })  // bare client for the token GET —
    {                                                        // reusing this pipeline would re-enter
      InnerHandler = new HttpClientHandler()                  // the handler that is mid-fetch
    }
  })
{
  BaseAddress = builder.HostEnvironment.BaseAddress,      // same origin → the cookie flows
  Timeout     = TimeSpan.FromMinutes(4),
}
Same origin is what makes the BFF model work: the client never sets an Authorization header because it has nothing to put in one.
