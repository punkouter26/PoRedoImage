Enforced budgets, not SLA targets

The repository defines no latency SLO. The ceilings a user actually experiences are: 4 minutes total on the browser's HttpClient, 5 minutes total on the server's outbound generative client (2 minutes per attempt, 2 retries), 10 requests/minute on the AI endpoints that carry the policy, and 25 MB of request body. A bulk batch is bounded by the same per-call budget applied under a concurrency cap, not by a batch-wide deadline.

Video is the one path with a budget of a different kind. Because it is a start-then-poll operation rather than one long call, its ceiling lives on the client: a 6-second poll interval against an 8-minute CancellationTokenSource, chosen so a slow-but-healthy render still lands rather than polling forever. The server never blocks on the render at all.

Video generate

POST /api/video/generate   VideoGenerateRequest  -> 200 VideoGenerateStartResponse
     { imageData, contentType, prompt }              { operationName }
     prompt: [Required, StringLength(1200, MinimumLength = 3)]

     503 "Video Unavailable"          — Google:ApiKey missing; checked FIRST,
                                        so an unconfigured server spends nothing
     400                              — empty prompt, or a failed magic-byte check
     422 "Video Generation Declined"  — the provider answered 4xx; its own message
                                        is passed through, because the difference
                                        between a filtered photo, an exhausted
                                        quota and a malformed request is the whole
                                        of what the user can act on
     502                              — the provider is unwell, or an unknown fault

GET  /api/video/status?op=<handle>  -> 200 VideoGenerateStatusResponse
     { done, videoData?, videoContentType?, errorMessage? }
     400  — handle missing, containing "..", leading "/", or lacking "operations/"
     502  — poll failed

     done=true with no clip is NOT an error status: it returns
     { done: true, errorMessage: "The video service returned no clip." }

Both endpoints sit in one group with .RequireAuthorization() and .RequireAntiforgeryValidation(). The filter only validates state-changing verbs, so the status GET passes through it untouched. Neither endpoint carries the ai-endpoints rate-limit policy.

Validation middleware logic

Three filters compose on a route group, and order matters — they run in registration order, so idempotency wraps antiforgery wraps validation.

// 1. IdempotencyKeyFilter — opt-in, never breaks a caller that omits the header.
if (!Request.Headers.TryGetValue("Idempotency-Key", out var raw)) return await next(ctx);
if (!IdempotencyKey.TryParse(raw, out var key))
    return Results.Problem(status: 400, title: "Invalid Idempotency Key");

cacheKey = $"idem:{userId ?? "anonymous"}:{key:D}";
if (cache.TryGetValue(cacheKey, out CachedResponse hit)) {
    Response.StatusCode = hit.StatusCode;
    Response.Headers["Idempotent-Replay"] = "true";
    await Response.WriteAsync(hit.Body);
    return Results.Empty;                 // short-circuit; already written
}
// First call: a TeeStream mirrors every write to the socket AND a buffer, the
// IResult is executed here so it flows through the tee, then Results.Empty stops
// the framework re-executing and overwriting the response. TTL 24 h.

// 2. AntiforgeryValidationFilter — safe methods pass straight through.
if (!IsUnsafeMethod(Request.Method)) return await next(context);
try   { await antiforgery.ValidateRequestAsync(http); }
catch (AntiforgeryValidationException) {
    return Results.Problem(status: 400, title: "Invalid antiforgery token", detail: ...);
}
// The exception message names the missing cookie or header — useful in a log,
// deliberately not echoed to the caller.

// 3. ValidationFilter<T> — DataAnnotations over the bound DTO.
if (!Validator.TryValidateObject(arg, ctx, results, validateAllProperties: true))
    return Results.Problem(status: 400, title: "Validation Error",
                           detail: string.Join("; ", results.Select(r => r.ErrorMessage)));
Two things to keep in mind when adding an endpoint

Apply .RequireAntiforgeryValidation() at the group, so a POST added inside an existing group is protected by default rather than by memory. And any new fallback path must set a user-facing reason — a degraded result with no explanation is treated as a defect in review, not as graceful handling.
