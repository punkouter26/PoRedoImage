Roles & Permissions

A backend-for-frontend where the browser never holds a token, authorization that fails closed by default, and the single hand-written escape hatch that keeps the app able to boot.

The security posture in four numbers

TIER 1
0
Tokens in the browser
The server serialises a claims-only principal to WASM. AddOidcAuthentication() and every token-handling API in that package are forbidden on .Client.
3
Authentication modes
Resolved once at startup by AddPoRedoImageAuth. Two of them refuse to exist in Production.
12
Route groups
Seven require an authenticated user, five opt out explicitly. Nothing is unprotected by omission.
1
Anonymous escape hatch
A middleware that stamps AllowAnonymous onto /_framework endpoints. Remove it and the app never boots.

Why the Test environment is named explicitly

The cookie-only branch was once gated on IsDevelopment() alone, so Test fell through to the OIDC branch and constructed the handler with an empty ClientId. It threw, and the entire integration suite broke. Both cookie policies now use IsDevOrTest() — and they must agree: gating only one of them is what produced a run where /dev-login answered 302 with a Set-Cookie the browser silently discarded, and every UI test landed back on /login.

Antiforgery tokens are identity-bound

A token issued while anonymous stops validating the moment the caller signs in. AntiforgeryTokenHandler's single retry-on-400 exists for exactly that, and a 400 on a first authenticated write is normal rather than a fault.

Why the filter, not the middleware

app.UseAntiforgery() alone does nothing for this API: it validates only what it recognises as a form post, so a JSON POST sails through regardless of its IAntiforgeryMetadata. Enforcement lives in AntiforgeryValidationFilter, applied at the group level so a POST added to an existing group is protected by default rather than by memory. Do not additionally set RequiresValidation = true — the middleware then marks the request unvalidated and the filter's own guard rejects even correct tokens.

Why /_framework is stamped anonymous

Most boot assets are static files covered by MapStaticAssets().AllowAnonymous(). The runtime-generated boot manifest is not a static asset, so the fail-closed fallback policy 302s it to /login; the browser follows the redirect, receives login HTML instead of a JS module, fails the subresource-integrity check, and renders a blank page. Routing has already matched the endpoint by that point, so the middleware clones its metadata with an AllowAnonymousAttribute appended. Every endpoint without the prefix stays fail-closed.

Policy configuration

TIER 3

The fail-closed default

options.FallbackPolicy = new AuthorizationPolicyBuilder()
    .RequireAuthenticatedUser()
    .Build();
Applies to every endpoint that declares no authorization metadata of its own — including one added tomorrow. Opting out is a deliberate .AllowAnonymous() call, never an omission.

The one named policy

options.AddPolicy("DiagnosticsAccess", policy =>
{
    policy.RequireAuthenticatedUser();

    // Production only: an explicit allow-list.
    if (environment.IsProduction())
    {
        var admins = config["Diagnostics:AdminEmails"]
            .Split(',', RemoveEmptyEntries | TrimEntries);

        // Fail closed — an empty list denies everyone.
        policy.RequireAssertion(ctx =>
            admins.Length > 0 &&
            ctx.User.Claims.Any(c =>
                c.Type is Email or Name
                       or "email" or "preferred_username"
                && admins.Contains(c.Value, OrdinalIgnoreCase)));
    }
});
The policy name lives in Features/Shared, not in the Auth slice: a policy is inherently cross-slice — Auth defines it, Diagnostics requires it — so both depend on shared vocabulary rather than on each other.

Issuer validation under OIDC

// AzureAd:AllowedTenantIds set → an explicit ValidIssuers list.
options.TokenValidationParameters.ValidIssuers = allowedTenants
    .Select(t => $"https://login.microsoftonline.com/{t}/v2.0").ToArray();

// Absent → any well-formed Entra issuer, malformed strings rejected.
options.TokenValidationParameters.IssuerValidator = (issuer, _, _) =>
    issuer is { } i
    && i.StartsWith("https://login.microsoftonline.com/", OrdinalIgnoreCase)
    && i.EndsWith("/v2.0", OrdinalIgnoreCase)
        ? i
        : throw new SecurityTokenInvalidIssuerException($"Untrusted issuer: {issuer}");
This preserves the intended multi-tenant plus personal-account behaviour under the common authority while still rejecting the unexpected issuer strings an unvalidated Authority setting could otherwise produce.

Denial payloads

TIER 3

API paths must never receive a redirect. Both the cookie handler and the OIDC handler special-case /api and answer 401 instead of challenging — without that, a WASM fetch follows the redirect to the Microsoft login page and fails opaquely.

401 — no principal on an API path

HTTP/1.1 401 Unauthorized
X-Correlation-ID: 6c1f…  X-Session-ID: 4a90…
(empty body — the handler sets the status and returns)
Non-API paths get the normal 302 to /login instead.

400 — antiforgery

HTTP/1.1 400 Bad Request
Content-Type: application/problem+json
{ "title": "Invalid antiforgery token", "status": 400 }
Expected once, on a first authenticated write. The client's handler refetches the token and replays the request with its correlation headers intact.

403 — authenticated but not permitted

HTTP/1.1 403 Forbidden
// GET /api/diag in Production by a signed-in user
// whose email is not in Diagnostics:AdminEmails —
// including when that list is empty.

429 — AI rate limit

HTTP/1.1 429 Too Many Requests
// Sliding window: 10 permits / 60 s, 6 segments,
// queue limit 2, oldest-first. Partition key is
// NameIdentifier, else remote IP, else "anonymous".
400 — malformed idempotency key

The Idempotency-Key header is optional, but a present-and-invalid value is rejected with a problem response naming the expected UUID shape rather than being ignored.
