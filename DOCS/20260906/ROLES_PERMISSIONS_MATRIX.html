Report 02 · Roles & permissions

Who Can Do What, and Why

Three auth modes resolved at startup, a fail-closed default that makes every new endpoint private by accident-proof design, and exactly one policy that does more than check for a signed-in user.

The deliberate asymmetry

Costly AI endpoints are anonymous; cheap storage endpoints are authenticated. That is intentional — the AI endpoints do not use caller identity, so requiring a cookie would buy nothing, and the rate limiter partitions by user id falling back to remote IP. It does mean an unauthenticated caller can spend the deployment's AI budget at 10 requests per minute per address.

Tier 3 · Implementation

Policies, bindings and error payloads

Policy definitions

options.FallbackPolicy = new AuthorizationPolicyBuilder()
    .RequireAuthenticatedUser()
    .Build();

options.AddPolicy(AuthorizationPolicies.Diagnostics /* "DiagnosticsAccess" */, policy =>
{
    policy.RequireAuthenticatedUser();
    if (environment.IsProduction())
    {
        var admins = (configuration[ConfigKeys.DiagnosticsAdminEmails] ?? "")
            .Split(',', RemoveEmptyEntries | TrimEntries);

        // Fail closed: with no configured admins, nobody reads prod diagnostics.
        policy.RequireAssertion(ctx =>
            admins.Length > 0 &&
            ctx.User.Claims.Any(c =>
                (c.Type is ClaimTypes.Email or ClaimTypes.Name
                        or "email" or "preferred_username")
                && admins.Contains(c.Value, OrdinalIgnoreCase)));
    }
});

The policy name lives in Features/Shared/AuthorizationPolicies.cs while its behaviour lives in the Auth slice. Slices must not reference each other, and a policy is inherently cross-slice — Auth defines it, Diagnostics requires it — so both depend on shared vocabulary instead of on each other.

Ownership is checked in the service, not the policy

/api/user-images/{id} takes the caller's NameIdentifier and passes it to IUserImageService, which scopes the Table Storage query by PartitionKey = userId. There is no resource-based authorization handler; the partition key is the boundary. A missing or foreign id returns 404, not 403 — which is the right disclosure behaviour but means an authorization bug here would read as “not found” in the logs.

Note also that /api/meme-templates/render carries a code comment saying “no auth required”, but it is registered inside a group with .RequireAuthorization(). The group wins; the comment is stale.

The video slice has no rate limit

/api/video is the only AI route group that does not call .RequireRateLimiting("ai-endpoints"), and it is the most expensive action in the app — $0.40 per clip, about ten image generations. Authentication and CSRF do bound it to signed-in callers, which the anonymous AI endpoints are not, so it is not open to the world; but a signed-in caller faces no throughput cap at all.

The status poll shares that group, so it is authenticated too. Its own guard is a shape check on the operation handle — the value comes from the client and reaches the provider URL as a path segment, so anything containing .., starting with /, or missing operations/ is rejected with a 400 before the outbound call is built.

Antiforgery binding

// Registration — Program.cs
options.HeaderName        = "X-CSRF-TOKEN";
options.Cookie.HttpOnly   = true;
options.Cookie.SameSite   = SameSiteMode.Strict;
options.Cookie.SecurePolicy = env.IsDevOrTest()
    ? CookieSecurePolicy.SameAsRequest    // Test runs over plain HTTP; Always THROWS
    : CookieSecurePolicy.Always;          // from GetAndStoreTokens on a non-SSL request

// Application — always at the GROUP level, so a newly added POST inside an
// existing group is protected by default rather than by memory.
var group = app.MapGroup("/api/user-images")
    .RequireAuthorization()
    .AddEndpointFilter<IdempotencyKeyFilter>()
    .RequireAntiforgeryValidation();

Do not additionally set RequiresValidation = true: the middleware then marks the request unvalidated, the filter's own check trips that guard, and even correct tokens are rejected. Tokens are identity-bound, so one issued while anonymous stops validating after sign-in — AntiforgeryTokenHandler's single retry-on-400 exists for exactly that, and firing on a first authenticated write is normal, not a bug.

401 / 403 payloads (RFC 7807, superseded by RFC 9457)

The shapes differ by where the rejection happens, and this is worth knowing before you write a client:

// (a) Rejected by the authentication pipeline — bare status, EMPTY body.
//     AddProblemDetails() is not registered, so there is nothing to serialize.
HTTP/1.1 401 Unauthorized
(no body)

// The redirect that would otherwise happen is suppressed for API paths:
//   OnRedirectToLogin            -> 401 when path starts /api
//   OnRedirectToIdentityProvider -> 401 when path starts /api
// Without those, a WASM fetch would follow a 302 to the Microsoft login page
// and fail opaquely.

// (b) Rejected by the DiagnosticsAccess policy — bare 403, empty body.
HTTP/1.1 403 Forbidden

// (c) Rejected by an endpoint filter or handler — full RFC 9457 document.
HTTP/1.1 400 Bad Request
Content-Type: application/problem+json
{
  "type":   "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title":  "Invalid antiforgery token",
  "status": 400,
  "detail": "The request did not include a valid antiforgery token. Fetch one
             from /api/antiforgery/token and resend it in the X-CSRF-TOKEN header."
}

// (d) Rate limited. Note: /api/video is NOT in this policy.
HTTP/1.1 429 Too Many Requests

// (e) Unknown /api path — deliberately a JSON 404, never the SPA shell.
HTTP/1.1 404 Not Found
Client contract

Treat 401 with an empty body as “sign in”, and 400 with problem+json titled Invalid antiforgery token as “refresh the token and replay once” — which is precisely what AntiforgeryTokenHandler does. Do not parse a body on 401 or 403; there isn't one.

Cookie hardening

The two application cookies must agree on SecurePolicy. Gating only one of them is what produced a real failure: over plain HTTP the browser silently discarded the auth cookie, /dev-login still answered 302 with a Set-Cookie, the request looked fine in the log, and every UI test landed on /login instead of the page it asked for.
