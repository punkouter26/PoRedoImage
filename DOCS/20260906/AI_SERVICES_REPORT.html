Providers, Routing and Cost

Seven execution locations, two per-request routers, one startup-resolved chat backend — and a failure model where a dead provider still reports green.

Latency budgets

These are enforced ceilings, not measured percentiles — the repository publishes no latency SLO. The three values on the generative client are interdependent and validated at startup: TotalRequestTimeout ≥ AttemptTimeout, and CircuitBreaker.SamplingDuration ≥ 2 × AttemptTimeout. Change one and the app throws on boot unless you check the others.

Cost projection per run

Two operations dominate the bill

One Veo clip costs $0.40. Veo 3.1 Lite at 720p is $0.05 per second and every render is eight seconds, so the model id is the price. A full 10-slot bulk board costs ≈$0.391 — one shared description call plus ten generated images. The two land within a cent of each other, and each is roughly 9× the most expensive single-photo run and about 160× a meme.

That is why the batch endpoint fans out under a concurrency cap, why Google:Imagen3FastModel exists as a cheaper image tier, and why Google:VeoModel defaults to the Lite variant rather than full Veo.

Video pricing is a code default, not configuration

AiPricingOptions.VideoGenerationUsd defaults to 0.40m in C#, and appsettings.json carries no AiPricing:VideoGenerationUsd entry — unlike vision, reasoning and music, which are all written out there. The estimate the user sees is correct today, but it is detached from the file an operator would think to edit.

Tier 2 · Architectural

Fallback, retry and circuit-breaking

Two layers absorb failure independently: the HTTP resilience pipeline retries and trips a breaker; the application layer catches whatever survives and substitutes a degraded result. The second layer is the dangerous one.

Vision routing — matched on namespace, never on a model-name prefix

The failure mode to understand

Callers of chat, vision and image services catch failures and substitute canned output, so a broken provider degrades several features while /health still reports green. That is exactly what the HuggingFace removal was about: its fal-ai routing returned HTTP 400 for every configured model id and the account's credits were depleted (402), while every caller silently substituted canned output.

Two live examples right now. Azure Computer Vision's Caption and DenseCaptions are region-unavailable, so AzureVisionService falls back to joined tags on every call — the failing call is made at most once, then cached in _captionUnsupported. And when the vision call itself fails (429 is common), SceneDescriber falls back to that same tag list.

MockAiDelegatingHandler is a defence-in-depth budget guardrail: it blocks any outbound AI call while Mocks:UseMockAi=true. In mock mode the real clients are never resolved, so it only ever fires on a future regression — at which point it fails loud instead of spending a live token.

Error mapping at the edge

ImageValidationException                    -> 400  "Invalid Image"
InvalidOperationException("Gemini declined") -> 422  "Generation Declined"
ClientResultException, content_filter
   or content_policy_violation               -> 422  "Content Policy Violation"
ClientResultException  401 | 403             -> 503  "Service Unavailable"
RequestFailedException 401 | 403             -> 503  "Service Unavailable"
RequestFailedException 400                   -> 422  "AI Service Error" (+ ErrorCode)
anything else                                -> 500  "Processing Error"

// Video slice — a different mapping, because Veo reports its own reasons and
// those reasons are the whole of what the user can act on.
!IsConfigured                                -> 503  "Video Unavailable"
VideoGenerationException, Status 400..499     -> 422  "Video Generation Declined"
VideoGenerationException, anything else       -> 502  "Video Generation Declined"
any other exception on start or poll          -> 502  "Video Service Error"

The two vendors report content refusal under different codes and this endpoint talks to both: Azure OpenAI returns 400 (content_filter), OpenAI.com returns content_policy_violation. Matching only the latter left every Azure refusal falling through to the catch-all, so the caller saw an opaque 500 and had no idea a different photo would work. Neither SDK exposes the code as a typed member, so it is matched on the exception message.
