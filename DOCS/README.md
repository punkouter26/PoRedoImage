# DOCS — audit reports & the diagnostics pipeline

Eight self-contained HTML audit reports, plus the collector that feeds the diagnostics one
with real browser measurements.

## Everyday use

```bash
node DOCS/collect-vitals.mjs --runs 8   # collect fresh samples + rebuild the reports
```

That one command is idempotent and safe to repeat. Open `DOCS/DIAGNOSTIC_METRICS.html`
afterwards. Everything else below is for when something is missing or you want to change how
the reports are built.

## Build markers

`build.mjs` resolves these in `_src/pages/*.html`, then fails if any are left unresolved:

| Marker | Replaced with |
|---|---|
| `<!--@STYLE-->` | `_src/partials/theme.css` |
| `<!--@SHELL-->` | `_src/partials/shell.js` (theme toggle, chart theming) |
| `<!--@CHARTJS-->` | The vendored Chart.js build |
| `<!--@SVG:name-->` | `_src/diagrams/out/name.{light,dark}.svg`, both inlined and id-namespaced |
| `<!--@RAIL:file-->` | Cross-report navigation, current page marked |
| `<!--@HISTORY-->` | `diagnostic_history.json` as `window.VITALS_HISTORY`, or `null` if absent |

Reports are inlined rather than linked because they are opened over `file://`, where fetching
a sibling asset is blocked.

```bash
node DOCS/build.mjs              # recompile diagrams (slow) + build reports
node DOCS/build.mjs --no-mmd     # reuse compiled SVGs (fast)
```

## The vitals pipeline

`diagnostic_history.json` is **not** hand-written. It is exported from data the application
itself collects. Five parts, all required:

| # | Part | Where |
|---|---|---|
| 1 | Browser collector — navigation timing, CLS, JS + WASM heap | `src/PoRedoImage.Client/wwwroot/js/vitals.js` |
| 2 | Script tag, **before** `blazor.web.js` | `src/PoRedoImage.Web/Components/App.razor` |
| 3 | Reporter + layout probe | `src/PoRedoImage.Client/Diagnostics/ClientVitalsReporter.cs`, `Shared/ClientVitalsProbe.razor` |
| 4 | `POST` / `GET /api/diag/vitals` | `src/PoRedoImage.Web/Features/Diagnostics/VitalsEndpoints.cs` |
| 5 | Table Storage persistence | `src/PoRedoImage.Infrastructure/Repositories/AzureTableClientVitalsRepository.cs` |

Supporting types: `Shared/DTOs/ClientVitalsDtos.cs`, `Domain/Entities/ClientVitalsSample.cs`,
`Domain/Interfaces/IClientVitalsRepository.cs`. Registered in
`InfrastructureServiceExtensions` and mapped in `Program.cs` (`MapVitalsEndpoints`, plus the
`telemetry` rate-limit policy).

Two details that are load-bearing:

- **Order of the script tag.** `vitals.js` installs a `layout-shift` observer at parse time. Put
  it after `blazor.web.js` and the boot's own layout shift goes unmeasured — the one shift a
  WebAssembly app most needs to see.
- **`interactiveMs`, not `loadMs`.** The document's `load` event fires in ~30 ms here, because
  `blazor.web.js` starts the runtime asynchronously afterwards. Time-to-interactive is measured
  from inside the running app at first render, and is ~900 ms. Charting `loadEventEnd` would
  show a flat, flattering line while the user watched a spinner.

### If `collect-vitals.mjs` is missing

Recreating it alone only helps if parts 1–5 above still exist — otherwise there is nothing to
collect and it will report zero samples. Check those files first.

The script's contract, in order:

1. Ensure Azurite is up: probe `127.0.0.1:10002`; if it is not answering, `docker start` a
   container matching `name=azurite`. Warn and continue if Docker is unavailable.
2. Probe `{base}/alive`. If it answers, reuse that instance and **do not stop it later**.
   Otherwise `dotnet build`, launch `src/PoRedoImage.Web/bin/Debug/net10.0/PoRedoImage.Web.exe`
   directly (not `dotnet run` — that wrapper orphans the app when killed) with
   `ASPNETCORE_ENVIRONMENT=Development`, `ASPNETCORE_URLS={base}`, `Mocks__UseMockAi=true`,
   `Storage__ConnectionString=UseDevelopmentStorage=true`, and wait for `/alive`.
3. Resolve `puppeteer` from `DOCS/_src`; `npm install` there if absent. Sign in via
   `{base}/auth/login/fake?email=…`, then do `--runs` full page loads across the feature routes,
   waiting ~4.5 s after each so the reporter's settle window elapses. Count `202`s.
4. `node DOCS/export-vitals.mjs --base … --days … --keep …`
5. `node DOCS/build.mjs --no-mmd`
6. Stop the app **only** if step 2 started it — including on failure or Ctrl-C.

### Flags

```bash
node DOCS/collect-vitals.mjs --runs 20                     # more samples per run
node DOCS/collect-vitals.mjs --replace                     # fresh history, don't append
node DOCS/collect-vitals.mjs --no-browser                  # export what's already stored
node DOCS/collect-vitals.mjs --base http://localhost:4100  # spare port
node DOCS/collect-vitals.mjs --keep 5000                   # raise the history cap
```

`export-vitals.mjs` additionally takes `--cookie` (required against a non-Development instance,
since `GET /api/diag/vitals` is behind the `DiagnosticsAccess` allow-list) and `--since <iso>`.

History **accumulates**: the export merges on `(timestamp, route)`, so samples that have aged
out of the server's query window survive in the file. `--keep` (default 1000) bounds growth.
Rows written before `interactiveMs` existed come back as `0`, which is impossible for a real
sample; the export drops them and prints how many.
